2026-11-03。指示書 v3.0「2-3. 実装前の調査」への回答。**評価の計算はまだ変えていない。**

表記: **確認済み** = テスト用データで動かして確かめた / **コード上** = コードを読んで分かった / **未確認** = 実際の COROS のデータが必要

## 1. 区間の情報がどこで失われるか (データの流れ)

| 段階 | ファイル・関数 | 区間の情報 | 根拠 |
|---|---|---|---|
| ① COROS のラップ API | `coros.ts` `importOne` → `queryActivityLapData` | `lapGroups` (ラップのグループが複数) を受け取る。中に区間の種類 (アップ・メインなど) があるかは**未確認** | コード上 |
| ② ラップの変換 | `coros.ts` `buildExt` | **ラップの数が一番多いグループだけ**を使い、距離・時間・平均心拍・ピッチだけに変換。グループの種類や、ラップごとの種類・ステップの項目は**捨てている**。1km ごとの自動ラップのグループの方がラップが多いので、ワークアウトのステップのグループがあっても使われない可能性が高い | コード上 |
| ③ FIT ファイル | `fit.ts` `parseFit` | session・lap・record・activity だけを読む。lap の区間の種類 (`intensity`)・ステップ番号 (`wkt_step_index`)、workout・workout_step のメッセージは**読んでいない** | コード上 |
| ④ 保存 | `ext.ts` `saveExt` (`ext_activities`) | 変換後のラップと 1 秒ごとの記録だけを保存。**元のラップ API の返り値と FIT は保存していない** → 保存済みのデータからは区間を復元できない | コード上 |
| ⑤ 評価 | `evaluate.ts` `evaluateRun` | 区間を知る方法は **STRIDE の計画の `steps` だけ** (`stepWindows`)。ステップの無い計画では、M・LT・レースは「目標帯の遅い側 +20 秒より速い記録」だけを評価に使う | コード上・確認済み (下の 2.) |
| ⑥ 分析・レビュー・画面 | `analysis.ts`・`runreview.ts`・`app.js` | ⑤ の結果 (評価区間の平均・距離) を表示するだけで、区間の境界・根拠は持っていない | コード上 |

## 2. テスト用データで確かめたこと

1 記録 15km = アップ 3km (5:30) + メイン 10km (8km を 4:30・最後の 2km が 4:55 に失速) + ダウン 2km (5:40)。計画は M ペース走 4:28〜4:32。

| 計画 | 評価に使った区間 | ペースの点 | 総合点 | 判定 |
|---|---|---|---|---|
| ステップあり (3km + 10km + 2km) | メイン 10km (失速の 2km を含む) | 73 | 77 | 正しい: 失速が採点に入る |
| ステップあり・失速なし | メイン 10km | 100 | 95 | 正しい |
| **ステップなし** | **8km だけ** (失速の 2km が、アップ・ダウンと一緒に除かれる) | **100** | **100** | **誤り: 失速した方が点数が高い** |

→ **S-01 (確認済み・重要度 高)**: 計画にステップが無いと、メインの途中の失速 (目標帯 +20 秒/km より遅い区間) が評価から消える。指示書の懸念 (「遅いという理由だけで除外しない」) は、ステップの無い計画では実際に起きている。テストは `test/known-issues.test.ts` の [S-01] (未修正なのでスキップ)。

## 3. 実際の COROS のデータで確かめる必要があること (未確認)

コードからは、COROS が区間の情報を**提供しているか**は分からない。そこで、ランの詳細画面に**調査用のボタン**を追加した (読み取りだけ・保存しない・評価を変えない)。

- 場所: COROS から取り込んだランの詳細の一番下「COROS のワークアウト区間を調べる (調査用)」→「調べる」
- 中身: ラップ API のグループごとの項目とラップ (最大 40 本)、取り込みでどのグループを使っているか、FIT のメッセージの種類と件数、FIT の lap の区間の種類・きっかけ・ステップ番号、workout_step (ステップ名・長さ・目標)
- 出さないもの: トークン・ID の全体 (末尾 4 桁だけ)・位置情報
- 回数: COROS の FIT のダウンロードを 1 回使う (1 日の上限があるので、押したときだけ)
- API: `GET /api/activities/:id/coros-segments` (`src/fitprobe.ts`)

確かめたいラン:
1. 11/1 の 12km 走 (アップ・ダウンを別に記録したか、1 記録か)
2. 1 記録の中にアップ → メイン → ダウンがある M ペース走か LT 走 (COROS のワークアウトで走ったもの)
3. インターバル (疾走とレストがあるもの)
4. ワークアウトを使わずに走ったラン (比較用)

## 3-1. 調査結果 (1): 11/1 の 12km 走 (2026-11-03 ユーザーが実行)

- ラップ API のグループは 4 つ: `type 2` = 1km ごと (13 本)・`type 11` = 5km ごと (3 本)・`type 12` = 10km ごと (2 本)・`type -1` = 全体 (1 本)。どれも**距離で自動に区切ったラップ**で、ワークアウトの区間のグループは無かった
- ラップの項目 (lapIndex・distance・time・avgPace・avgHr・avgCadence・avgStrideLength・groundTime・avgPower など) に、区間の種類 (アップ・メイン・ダウン・レスト) を表す項目は無かった
- 取り込みが使っているのはグループ 1 (1km ごと)。このランでは正しい選び方
- FIT: COROS の 1 日の上限 (50 件) に達していて読めなかった → 翌日以降にもう一度
- このランはメインだけの記録 (アップ・ダウンは別の記録)。指示書の「複数の活動に分かれているケース」にあたる。区間の判定はこの記録では不要
- まだ分からないこと: **COROS のワークアウトで走った記録**に、区間のグループ (type 2・11・12・-1 以外) や FIT の区間の種類が出るか。ワークアウトで走ったポイント練・インターバルの調査結果が必要

## 4. 区間の決め方 (案) — 調査結果を見てから固める

| 優先 | 根拠 | 使う条件 |
|---|---|---|
| 1 | **COROS のワークアウト** (FIT の lap の `intensity`・`wkt_step_index`、または ラップ API の区間の種類) | ステップの情報があり、区間の距離・時間の合計が記録の合計と合う (±2%) |
| 2 | **STRIDE の計画の steps** | 1 が無い。計画の合計距離と記録が合う。境界は距離で当てる (今の `stepWindows`) |
| 3 | **手動で指定** | 1・2 が無いか、ずれているとき。ランの詳細で境界を直せるようにする (画面は第3段階) |
| 4 | **推定・未確定** | どれも無い。評価は「参考」と表示する。**ペースだけでメインを決めない** |

- インターバル: 疾走とレストを別に集計 (疾走の本数・各本のペース・目標との差・後半の落ち込み / レストの時間・距離)。レストは疾走のペース評価から除くが、全体の量・負荷には入れる
- アップ・ダウン: 「楽に走れたか」だけを見て、メインの未達として減点しない
- 量・合計距離・全体の負荷: アップ・メイン・ダウンをすべて含める
- 評価の保存: 今の JSON に、区間 (`segments`: 種類・開始・終了・距離・時間・根拠) と評価の版 (`version: 3`) を**追加**する。今のキーは変えない (日・週・月・適性・目標への現在地・シューズの相性が読んでいるため)
- 保存済みの評価は一括で直さない。再評価はユーザーが選んだランだけ

## 5. COROS の取り込みの変更が必要になった場合 (指示書 1-3 の例外)

調査の結果、区間の情報が FIT かラップ API にあれば、**取り込み済みのデータの「読み取り・保存」だけ**を最小限に広げる案を、変更前に報告する:

- 変える可能性があるファイル: `fit.ts` (lap の `intensity`・`wkt_step_index` を読む)・`coros.ts` `buildExt` (区間の情報を `act.segments` として**追加で**保存。今のラップの選び方は変えない)
- 変えないもの: 認証・トークン・Webhook・同期の順番と回数・重複の統合・ID
- 互換性: 追加の項目だけなので、今の画面・評価は今のまま動く
- 過去のラン: 保存済みのデータには区間が無いため、区間を使うには COROS から取り直しが必要 (設定の「直近14日を取り直す」と同じしくみ)。どの範囲を取り直すかはユーザーが決める
